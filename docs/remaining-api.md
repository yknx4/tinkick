# Remaining API inventory — 2026-09-17

Baseline: Searchkick 6.1.2 / commit93e901a75b11a25101668a616e006b158251b16e, current Tinkick code, docs/compatibility.md, docs/plan.md, README. This is an implementation inventory, not a claim that every unimplemented behavior has a proven implementation design.

## Source corrections before defining completion

- Searchkick Relation#only/#except retain/remove QUERY OPTIONS; they are not column projections. They rebuild a relation from sliced options (relation.rb650–656). Tinkick must restore model/default query options correctly when fields/misspellings are removed.
- select/reselect control source retrieval, including scalar/array fields, true/false/[], includes/excludes, and wildcard field forms. Pinned select tests primarily assert raw load:false behavior; a block remains Enumerable selection. Model-loading selection is not automatically ActiveRecord#select.
- each_with_hit and with_details were removed (upstream CHANGELOG375–376); use with_hit.each and with_highlights. Query's stale delegations do not make them supported6.1.2 results methods.
- Native backend semantics govern compatibility: retain direct TIN/PostgreSQL operations, document differences, and reject explicit controls that require recreating Elasticsearch or Lucene internals. Earlier custom refinement engines have been removed.

## Dependency-ordered native integration work

1. **Core result metadata.** scope_results, missing_records, misspellings? with exact-first retry, model_name/entry_name, cached client page timing through took, and error success semantics are implemented and tested. Database failures continue to raise; page metadata does not invoke result scopes/preloads or request totals.

2. **Projection and query option operations.** Top-level and nested JSON select/reselect source filtering, Enumerable block selection, hidden cursor-key preservation, only/except on options, explicit _score/compound ordering, and Searchkick-compatible wildcard search-field expansion are implemented. Wildcards expand known searchable fields and preserve per-field match/misspelling restrictions. Model results retain complete attributes according to pinned Searchkick behavior.

3. **Highlight public surface and portable response.** Cached hits/with_hit use durable model PK, PostgreSQL table identity, native score, and selected source snapshots; pre-scope hits and visible record pairs are tested. Cached response includes page timing, those hits, ordinary exact totals and requested aggregations; countless/keyset omit unknown totals without COUNT. Public highlight options, per-field configuration, highlights/with_highlights, record search_highlights, raw highlighted_* values, custom tags, HTML encoding and Unicode-safe snippets use native TIN spans for default-analysis modes. SQL whole-field highlighting verifies each page field through the matching predicate and marks the complete field. Non-default index tokenization raises Tinkick::NotImplementedError: implicit native highlighting rejects that configuration, and explicit highlighting uses default analysis. Custom source-span reconstruction and token reanalysis are intentionally excluded. Model highlight declarations validate fields lazily; query highlighting remains explicit, without term-vector storage.

4. **Finish lexical/filter controls.** Phrase exclusions, per-field misspellings, below-threshold retry, and native PostgreSQL regex filters have real database coverage. String regexp patterns pass unchanged to PostgreSQL ~, using native syntax and embedded flags. Ruby Regexp values raise Tinkick::NotImplementedError; no source or flag adapter is provided. Lucene intersection/complement and interval syntax are not emulated; use native patterns and SQL boolean filters. Regex scans log a cost warning. Arrays, JSONB leaves, canonical enums and optional-extension absence have live coverage. Explicit max_expansions and transpositions: true now raise Tinkick::NotImplementedError: these Elasticsearch controls are not supplied by native TIN. The previous dictionary-ranking and custom edit-distance emulation is removed; whole-token fuzzy matching uses native Levenshtein semantics. JSONB recursively nested scalar/object arrays and independent dotted-path filters are implemented, with exact-path verification and GIN equality candidates. The `id` filter uses the model's primary key, including custom and UUID keys. Object-container exists/nil checks inspect non-null descendants; equality/ranges/patterns keep exact-path semantics. Enum equality/in/all/negation use canonical serialized labels and bound backing values, including duplicate/nil/unknown backing mappings. Lexical label ranges and patterns use a warned SQL CASE expression. General nested-object correlation is not a Searchkick 6.1.2 high-level where operator; conversion ranking uses literal JSONB keys as described in package 5, while Elasticsearch body/mapping queries remain excluded. PostgreSQL scalar columns have no broad type rejection; nonprimitive Ruby filter values require separate serialization decisions. Native default expansion/score differences already approved remain intentional.

5. **Ranking and remaining aggregation shapes.** Native field ^boost from 0 through 10000 is implemented, including wildcard/default fields and per-field match modes. SQL field weights and larger factors use tested weighted branches with grouping/sorting cost warnings. Public boost_by numeric modifiers, missing values, numeric arrays and JSONB numeric paths are implemented without optional extensions. JSON paths coerce numeric strings, flatten arrays and report malformed matching values at scoring time. The legacy boost alias preserves its single-field replacement behavior and composition with numeric multiply functions. Conditional boost_where weights and fractional demotion use shared SQL filters, compose with numeric boosts, and warn about predicate/sort costs. Recency gauss/exp/linear functions support native date/numeric columns and arrays, missing values, offsets and weighted composition without optional extensions. Native conversions/conversions_v1/conversions_v2 ranking, field selectors, conversions_term and v2 factors are implemented over application-owned JSONB columns. Both-version declarations default to legacy; an explicit transition disables legacy and enables v2. Keys remain literal, with native PostgreSQL lower or exact lookup under case_sensitive: true, and scoring logs sort/JSONB iteration costs. Conversion stemming and external analytics/index lifecycle are intentionally excluded. See [the conversion contract](conversions-contract.md) and [query plans](conversion-plans.md). JSONB recency paths deliberately require typed stored/generated date or numeric columns; Tinkick reports an actionable query error instead of inferring types from JSON values. Timestamp-string casts need ordinary maintained columns unless a valid immutable generated expression is available. Numeric histograms with bounds, calendar/fixed date histograms with fixed offsets and IANA zones, compound relevance ordering, ISO/epoch date labels, signed date bucket offsets, and extended/hard date histogram bounds are implemented. Date arrays and joined rows count each document once per date bucket. Calendar and fixed date intervals use native PostgreSQL date_trunc/date_bin and generate_series with dense-grid cost warnings. Elasticsearch date math and Java-format translation are deliberately absent; use application-computed Date/Time boundaries and application labels. Smart facets preserve the lexical/model scope and follow Searchkick filtering rules: smart_aggs: false ignores global where while retaining per-aggregation filters. Terms include/exclude filter bucket values before limits using bound exact arrays or native PostgreSQL regex strings, with regex cost warnings. Ruby Regexp/Elasticsearch partition hashing are excluded. Terms, metrics, numeric/date ranges and histograms support missing defaults using bound COALESCE with one fallback per null/empty/all-null array document; scopes, duplicate metric values and zero-count dictionaries are preserved. DATE replacements preserve calendar values; timestamp replacements use normalized instants. Scalar JSONB aggregation fields remain follow-up work. JSONB aggregation array flattening is outside the first version by explicit user choice. General subaggregations use the excluded Elasticsearch body_options DSL; Java numeric format patterns are also excluded. Use native SQL grouping/subqueries and application number formatting, without adding a DSL or format translator. Native implementations require NULL/array semantics, cost warnings and real plans. Model/indices boosts wait for multi-model identity; geographic distance boosts wait for geo integration.

6. **Analysis and model configuration.** case_sensitive/special_characters declarations validate native index policies and control SQL text normalization; omitted versus explicit nil and optional unaccent are tested. The independent Tinkick.models registry records successful loaded declarations without database queries or inherited duplicates. Native STI parent/child/descendant records, counts and SQL aggregates are tested; aggregate wrappers preserve the inner class restriction. Remaining: emoji-name expansion; synonym configuration/refresh using explicit application data; explicit inheritance/type and unscope options. Filterable declarations validate physical columns and JSONB path roots lazily; they do not restrict SQL filtering or create indexes. Global model_options defaults are implemented with explicit per-model overrides and independent Searchkick configuration. Custom search_method_name is implemented with nonclobbering aliases and optional alias suppression. Keep should_index? migration explicit: arbitrary Ruby predicates cannot be inferred as SQL. Tenant boundaries cannot be discarded as an index-name no-op.

7. **Global search and integrations.** Explicit Tinkick.search(model:) is implemented. Remaining: models/multi-model search, multi_search populating relations and exposing individual errors, model-specific loads, UNION/merge ordering and model boosts, pagination-library contracts. ActiveSupport notifications for executed search pages/plucks, counts, and aggregations are implemented in the independent Tinkick namespace. PostgreSQL failed-query isolation needs actual savepoint/transaction tests. SQL-backed index inspection (exists?/tokens/total_docs) is feasible separately from excluded index lifecycle APIs.

8. **Optional search families, with explicit prerequisites.** Suggestions require candidate generation and phrase ranking; similar requires meaningful-term selection/thresholds; locations/geo_shape/distance ranking require verified geometry primitives (such as optional PostGIS); knn/semantic/hybrid retrieval requires verified pgvector/operator/index support and merge/ranking policy. These are research/design-dependent adapter families, not proven impossible in PostgreSQL or TIN. Feature-specific extension checks must happen only when requested.

## Actual native differences and intentional exclusions

- Documented native stemming/language-analysis absence is the currently evidenced search capability difference; the model raises a migration-oriented NotImplementedError. Persisted normalized columns or another explicitly designed SQL analysis path remain possible application strategies.
- TIN normalization, dense-term scoring, native fuzzy expansion and tie order differ from Lucene. The user approved native default scores and extra typo eligibility. Do not call these unfinished score-parity work unless an explicit option requests stronger semantics.
- Observed router helper-call restrictions have implemented SQL alternatives. The historical multi-field tin.score issue no longer reproduces in current regression checks; native multi-column scoring is restored. See [current plan evidence](query-plans.md#multi-column-recheck).
- External document import/reindex, synchronization callbacks/queues, Elasticsearch body/mappings/settings/HTTP transport, alias/index promotion, scroll IDs, and non-ActiveRecord/Mongoid backends are intentional exclusions or out-of-scope integrations. They must not masquerade as TIN limitations. Timers, SQL routing, and index inspection may still have useful adapter replacements.

## Deterministic completion criterion

The user clarified the priority on 2026-09-17: good enough practical search,
not perfect compatibility or exhaustive obscure features. The acceptance focus
is matching, relevance, filtering, result loading, pagination, Searchkick
coexistence, and real Rails usage, backed by the fixed 10,000-record stress test
and at least 90% line coverage. Secondary aggregation and analysis options stay
in this follow-up inventory; they do not need to delay a usable core gem.

Keep each entry honest: implemented with native tests, an intentional exclusion,
or unresolved follow-up work. Do not relabel unverified features as unsupported
by TIN. A usable core release does not claim complete Searchkick API parity.
